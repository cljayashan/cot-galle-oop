Exception Handling — When Things Go Wrong

Your earlier notes warned that Integer.parseInt("abc") crashes the program. This lesson shows how to catch that crash, recover gracefully, and keep the console program running — the professional way to handle unexpected situations in Java.

⏱ ~3 Hours Integrated 📋 Session A1.1 🔧 try / catch / finally / throw

Learning Outcomes — After this lesson you will be able to:

  • Explain what an exception is and why uncaught exceptions stop a program
  • Write try / catch / finally blocks for risky operations
  • Recognise common runtime exceptions (NumberFormatException, NullPointerException, ArithmeticException, …)
  • Use throw to signal invalid situations from your own methods
  • Build safer console input that does not crash on bad user typing

1. Why Exceptions Exist

  • Normal if checks handle expected cases; exceptions handle unexpected failures (bad input, missing object, divide by zero).
  • Without handling, the JVM prints a stack trace and ends main.
  • With handling, you show a friendly message and continue (e.g. ask the user to type again).

2. Core Syntax

try {
    // risky code
} catch (NumberFormatException ex) {
    // recovery for this exception type
} finally {
    // always runs (cleanup) — optional
}

You may stack several catch blocks (most specific first). A broad catch (Exception ex) is a last resort, not the first choice.

3. Common Exceptions in This Module

ExceptionTypical cause
NumberFormatExceptionInteger.parseInt("abc")
NullPointerExceptionCalling a method on null
ArithmeticExceptionInteger divide by zero
ArrayIndexOutOfBoundsExceptionBad array index
InputMismatchExceptionWrong type with Scanner.nextInt()

4. throw from Your Methods

Encapsulation often pairs with exceptions: a setter or withdraw can throw new IllegalArgumentException("...") instead of silently ignoring bad data. Callers then decide whether to catch and recover.

Lesson A1 Summary

  • Exceptions = unexpected runtime problems; uncaught → program ends.
  • try wraps risk; catch recovers; finally always runs.
  • Know the common exception names for exams and debugging.
  • throw lets your methods refuse illegal states clearly.
