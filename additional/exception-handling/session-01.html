Exception Handling

In Session 02 you saw that typing abc when a number is expected crashes the program with a NumberFormatException. Today we stop treating that as “don’t type badly” and learn to catch the problem, show a clear message, and keep the program alive — just like real console apps do.

⏱ ~3 Hours Integrated 📋 Session A1.1 🔧 Optional enrichment (not in L01–L10 sequence)

Learning Outcomes – After this session you will be able to:

  • Define an exception and explain what happens when it is not caught
  • Write try, catch, and finally blocks correctly
  • Identify common Java exceptions used in console programs
  • Use throw inside methods to refuse illegal arguments
  • Build a small menu that survives bad keyboard input

1. What Is an Exception?

An exception is an object that represents a problem that occurred while the program was running. The JVM creates it and “throws” it up the call stack. If nobody catches it, the program prints a stack trace and stops.

Definition — Exception

An exception is a runtime event that disrupts the normal flow of a program. Java represents it with a class that inherits from Throwable (usually via Exception or RuntimeException). Handling means catching that object and deciding what to do next.

Real-world analogy: you are following a recipe (normal flow). Suddenly the oven will not heat (unexpected problem). You do not abandon cooking forever — you notice the problem, decide a fix (use the microwave, or wait), then continue. That “notice and recover” step is exception handling.

Figure A1.1 — Uncaught exceptions end the program; caught exceptions let you recover.

1.1 Crash Demo (Do This First)

public class CrashDemo {
    public static void main(String[] args) {
        String text = "abc";
        int n = Integer.parseInt(text);   // NumberFormatException!
        System.out.println("This line never runs: " + n);
    }
}
Tip — Read the stack trace

The red error names the exception type, the message, and the line number (e.g. CrashDemo.java:4). In exams and labs, always say which exception and which line — that is half the mark.

2. try / catch / finally

Wrap the risky code in try. Write one or more catch blocks for the exception types you expect. Optionally add finally for cleanup that must run whether or not an exception occurred.

public class SafeParse {
    public static void main(String[] args) {
        String text = "abc";
        try {
            int n = Integer.parseInt(text);
            System.out.println("Number = " + n);
        } catch (NumberFormatException ex) {
            System.out.println("That was not a valid integer.");
            System.out.println("Details: " + ex.getMessage());
        } finally {
            System.out.println("Parse attempt finished.");
        }
        System.out.println("Program still running — success!");
    }
}
🧠 Beginner’s Logic Breakdown
  1. try = “attempt this; it might fail.”
  2. catch (Type name) = “if that failure is Type, run this recovery.” The variable ex holds the exception object (getMessage(), stack info).
  3. finally = “always do this next” — useful later for closing files/scanners. For now, think of it as a guaranteed epilogue.
  4. After a handled exception, execution continues after the whole try/catch/finally structure — your main does not die.

2.1 Multiple catch Blocks

Different problems need different messages. List specific types first; a general Exception catch may come last.

try {
    int a = Integer.parseInt(args[0]);
    int b = Integer.parseInt(args[1]);
    System.out.println("Quotient = " + (a / b));
} catch (ArrayIndexOutOfBoundsException ex) {
    System.out.println("Please provide two numbers as arguments.");
} catch (NumberFormatException ex) {
    System.out.println("Both arguments must be integers.");
} catch (ArithmeticException ex) {
    System.out.println("Cannot divide by zero.");
}
Note — Order matters

If you catch Exception first, the more specific catches below it become unreachable (compiler error). Always go from narrow → broad.

3. Exceptions You Will Meet Often

ExceptionWhen it appearsTypical fix / catch action
NumberFormatException Integer.parseInt / Double.parseDouble on bad text Ask user to re-enter; show “enter a number”
NullPointerException Calling a method on a null reference Check if (obj != null) before use (prefer prevention)
ArithmeticException Integer division by zero (10 / 0) Validate divisor ≠ 0 before dividing
ArrayIndexOutOfBoundsException Index < 0 or ≥ length Check bounds; use loop limits carefully
InputMismatchException Scanner.nextInt() when user types letters Catch, clear scanner buffer, ask again
IllegalArgumentException You (or a library) rejected a bad argument Catch at UI layer; fix the call site
Tip — Prefer prevention for null

For NullPointerException, catching is possible but usually worse than a clear if (found == null) check (as in the Library search). Use exceptions for truly exceptional input/state, not as a substitute for normal if-logic.

4. throw — Signalling Problems from Your Methods

Encapsulation already rejects bad data inside setters. Another professional pattern is to throw an exception so the caller must notice. This is useful when silent “print and return” is not enough.

public class BankAccount {
    private double balance;

    public void withdraw(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive.");
        }
        if (amount > balance) {
            throw new IllegalArgumentException("Insufficient funds.");
        }
        balance -= amount;
    }

    public double getBalance() { return balance; }

    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Deposit must be positive.");
        }
        balance += amount;
    }
}
public class BankApp {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount();
        acc.deposit(1000);
        try {
            acc.withdraw(1500);   // will throw
            System.out.println("Withdraw OK");
        } catch (IllegalArgumentException ex) {
            System.out.println("Withdraw failed: " + ex.getMessage());
        }
        System.out.println("Balance still: " + acc.getBalance());
    }
}
🧠 Beginner’s Logic Breakdown
  1. throw new … immediately leaves the method — later lines in that method do not run.
  2. The exception travels to the nearest matching catch. If main has none, the program still crashes.
  3. Message text in the constructor becomes ex.getMessage() — write clear, exam-friendly sentences.
  4. This pairs with OOP: the class protects its rules; the UI layer decides how to tell the user.
Note — Checked vs unchecked (exam awareness)

Most exceptions in this module are unchecked (RuntimeException family): you are not forced to declare them. Checked exceptions (e.g. some file I/O types) must be caught or declared with throws on the method. File I/O is outside the core console focus here — remember the names for theory questions.

5. Practical Pattern — Safe Menu Input Loop

Menus die when users type letters into a number prompt. A small helper method keeps the loop alive:

import java.util.Scanner;

public class SafeMenu {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        boolean running = true;

        while (running) {
            System.out.println("1. Say hello");
            System.out.println("2. Divide two numbers");
            System.out.println("0. Exit");
            System.out.print("Choice: ");

            int choice = readInt(sc);
            switch (choice) {
                case 1:
                    System.out.println("Hello, COT Galle!");
                    break;
                case 2:
                    System.out.print("Numerator: ");
                    int a = readInt(sc);
                    System.out.print("Denominator: ");
                    int b = readInt(sc);
                    try {
                        System.out.println("Result = " + (a / b));
                    } catch (ArithmeticException ex) {
                        System.out.println("Cannot divide by zero.");
                    }
                    break;
                case 0:
                    running = false;
                    break;
                default:
                    System.out.println("Unknown option.");
            }
        }
        sc.close();
        System.out.println("Goodbye.");
    }

    /** Keeps asking until the user types a valid integer. */
    private static int readInt(Scanner sc) {
        while (true) {
            String line = sc.nextLine();
            try {
                return Integer.parseInt(line.trim());
            } catch (NumberFormatException ex) {
                System.out.print("Please enter a whole number: ");
            }
        }
    }
}

Session A1.1 Summary

  • Exceptions interrupt normal flow; uncaught ones end the program with a stack trace.
  • try / catch / finally let you recover and continue.
  • Know NumberFormatException, NullPointerException, ArithmeticException, and friends.
  • throw enforces method rules; callers catch and display messages.
  • Safe input loops turn fragile menus into student-proof console apps.
