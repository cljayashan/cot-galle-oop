Abstraction – Abstract Classes vs Interfaces

The fourth OOP pillar: classes that exist only as concepts, and pure contracts unrelated classes can sign. Concludes with the Library System's final assembly using the Lendable interface.

⏱ 6 Hours Integrated 📅 Sessions 19 – 20 📚 Library Project Phase 6 (Final)

Learning Outcomes – After this lesson you will be able to:

  • Write abstract classes with abstract and concrete members
  • Define and implement interfaces; use them as variable types
  • Choose between abstract class and interface correctly
  • Identify all four pillars in one coherent codebase

1. Abstract Classes (Session 19)

abstract class Shape                       // cannot be instantiated - concept only
{
    public Shape(String name) { ... }      // constructors allowed - children call super(...)

    public abstract double area();         // NO body - every child MUST override

    public void describe()                 // concrete method may call the abstract one:
    {
        System.out.println(name + " has area " + area());   // template pattern
    }
}
  • Concrete overridable method = optional replacement with a default; abstract = mandatory, no default. Compiler-enforced. Use @Override.
  • Abstract classes model "is-a" families where the base is incomplete (Shape, LibraryItem).

2. Interfaces (Session 19)

import java.util.*;

interface Playable                        // pure contract - no fields, no bodies
{
    void play();
    void stop();
    int getDurationMinutes();
}

class Song implements Playable, Downloadable { ... }   // many interfaces - legal
class Movie implements Playable { ... }                  // unrelated to Song - still playable

void playAll(List<Playable> playlist) { ... }   // interface as a type

Rule of thumb: family + shared code → abstract class; capability across unrelated classes → interface. Syntax: class Book extends LibraryItem implements Lendable.

3. Library Phase 6 – Final (Session 20)

  • LibraryItem becomes abstract (blank items impossible); printDetails becomes abstract (every child forced to describe itself).
  • New Lendable interface — implemented by all library items and by standalone Equipment (projectors, laptops) that are not LibraryItems.
  • processAllLendable / lending status report builds one List<Lendable> from catalog + equipment — one loop across two family trees.
  • Assessed demo: run the workflow, point to each pillar in code, answer one "what if" design question.

  2. Explain the difference between an abstract method and an overridable concrete method. (4 marks)
  3. What is an interface? How does it differ from an abstract class? State three differences. (6 marks)

Lesson 09 Summary

  • Abstract classes model incomplete concepts; abstract members are mandatory contracts for children.
  • Interfaces are pure capability contracts stacking freely across families.
  • The Library System now demonstrates all four pillars — encapsulation, inheritance, polymorphism, abstraction — in one project.
