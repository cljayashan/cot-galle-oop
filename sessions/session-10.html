Lesson 04 of 10 — The First Pillar of OOP

Encapsulation

Until now our fields were public — anyone could write account.balance = -999999; and destroy the data. Encapsulation fixes this: we hide the data and expose only safe, controlled doors. This is the first and most fundamental of the four OOP pillars.

⏳ 10 Hours Integrated 📚 Sessions 07 – 09 🔒 Pillar 1 of 4

1. The Problem: Naked Data

Our Session 05 BankAccount had careful deposit() and withdraw() methods with rules… but the field was public, so this compiles and runs happily:

BankAccount acc = new BankAccount();
acc.balance = -1000000;              // bypasses ALL our rules - total disaster, no error!
acc.balance = acc.balance * 100;     // instant millionaire - the bank is ruined

Our rules were only suggestions. Real protection means making it impossible to bypass the rules — the compiler itself must refuse such code.

Definition — Encapsulation

Encapsulation is bundling data (fields) and the methods that operate on that data into one unit (the class), while hiding the data from direct outside access. Outsiders interact only through a controlled public interface. Also called data hiding.

Real-world analogies help us remember the idea:

  • ATM: the cash is locked inside the vault; you interact only through the keypad and card slot — the machine validates everything before money moves.
  • Medicine capsule: the drug is sealed inside a shell — you take the capsule as a whole; you cannot touch the powder directly.
  • Car pedals: you press the accelerator — you do not reach into the engine to squirt fuel into cylinders yourself.
Figure 7.1 — ATM analogy: outsiders use public methods (the keypad); private fields (the cash vault) stay hidden inside the class.

2. Access Modifiers — The Door Policy

An access modifier is a keyword written before a field, method or class that controls who can use it:

ModifierWho Can Access?Typical Use
publicAny code, anywhereMethods meant for outside use; the class’s “control panel”
privateOnly code inside the same classFields — almost always! Also internal helper methods
protectedSame class + its child classesComes alive in Lesson 06 (Inheritance)
package-private (default)Any code in the same projectAdvanced scenarios; Java classes default to this
Figure 7.2 — public vs private: public members form the safe interface; private members store and protect the real data.
Convention — Naming Private Fields

Private fields use camelCase (balance, ownerName). Public methods use camelCase (deposit, getBalance). This instantly tells every reader what is hidden and what is the public control panel.

2.1 Encapsulated BankAccount with Getters and Setters

// File: BankAccount.java  (version 2 - encapsulated)

    class BankAccount
    {
        // PRIVATE fields - invisible from outside the class
        private double balance;              // stores the account balance
        private String ownerName;             // stores the account holder's name

        // PUBLIC methods - the only doors into the object

        public void deposit(double amount)
        {
            // Reject invalid deposits before touching the balance
            if (amount <= 0)
            {
                System.out.println("deposit must be positive!");
                return;
            }
            balance += amount;                // inside the class we CAN touch balance
        }

        public boolean withdraw(double amount)
        {
            // Return false if the withdrawal is impossible
            if (amount <= 0 || amount > balance)
            {
                return false;
            }
            balance -= amount;
            return true;
        }

        // GETTER method: lets outsiders READ the balance without changing it
        public double getBalance()
        {
            return balance;                   // hands out a copy of the value
        }

        // SETTER method with validation: controlled writing of owner name
        public void setOwnerName(String name)
        {
            if (name == null || name.trim().isEmpty())   // empty or only spaces?
            {
                System.out.println("Owner name cannot be empty.");
                return;
            }
            this.ownerName = name;
        }

        public String getOwnerName()
        {
            return ownerName;
        }
    }

2.2 Seeing the Compiler Protect You (a compile-time access error)

// In Main:
BankAccount acc = new BankAccount();

acc.deposit(5000);                        // OK - public door
System.out.println(acc.getBalance());      // OK - reading through the getter: 5000

acc.balance = -1000000;                   // COMPILER ERROR!
// Error a compile-time access error: 'BankAccount.balance' is inaccessible due to its protection level
// The hack from Section 1 is now IMPOSSIBLE. The compiler is our security guard.
🧠 Beginner’s Logic Breakdown
  1. private = inside only. The methods of BankAccount (deposit, withdraw…) can read/write balance freely because they live inside the same class. Main lives in a different class, so its attempt fails at compile time — the program will not even build.
  2. Getter = read-only window. getBalance() hands out a copy of the value. The outsider can look, but not touch the field directly.
  3. Setter = guarded entrance. setOwnerName() checks the input first. Bad values bounce off. Every write goes through the checkpoint.
  4. a compile-time access error is the error code to remember in exams: “inaccessible due to its protection level.”

2.3 Deciding What to Expose

Design rule of thumb for every member you write:

  1. Fields → private, practically always.
  2. Methods that outsiders need → public.
  3. Helper methods used only internally (e.g. a ValidateAmount()) → private.
  4. When unsure → start private. You can always open a door later; closing a door that others already use breaks their code.

Session 07 Summary

  • Public fields let anyone bypass your rules; encapsulation makes bypassing impossible.
  • private = same class only; public = everyone; protected waits for inheritance.
  • Getter methods give read access; setter methods validate before writing.
  • Convention: camelCase private fields, camelCase methods; PascalCase only for class names.
  • Compiler error a compile-time access error proves the protection level is enforced at build time.
