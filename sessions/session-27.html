Lesson 08 of 10 — The Third Pillar of OOP

Polymorphism

Greek: poly = many, morph = form. The same method call — animal.makeSound() — produces a bark from a Dog and a meow from a Cat. The caller doesn't need to know or care which one it is talking to. This one idea powers most professional software design.

⏱ 4 Hours Integrated 📋 Session 17 of 23 🏛 Pillar 3 of 4

1. The Setup: A Child in a Parent-Shaped Box

First, a fact that surprises everyone: because a Car is a Vehicle, Java allows this:

Vehicle v = new Car("Toyota", 2022, 4);   // a Car stored in a Vehicle variable — LEGAL!
// Think: a Car parked in a space marked "Vehicles". Perfectly truthful.

v.accelerate();          // fine — Vehicles can accelerate
// v.openBoot();         // ERROR — the variable's TYPE is Vehicle, so only Vehicle
//                          members are visible through it, even though a Car is inside.

Why would we ever do this? Because it lets one variable (or one List!) handle any vehicle — car, bus or bike. But it raises the key question: if the child changed a method, which version runs through the parent-typed variable — the parent's or the child's?

Definition — Polymorphism (Runtime)

Runtime polymorphism lets a derived class provide its own implementation of a base-class method, and guarantees the derived version runs even when the object is accessed through a base-typed variable. Java enables it by default: instance methods are overridable unless marked final. Mark replacements with @Override.

1.1 The Classic Demo — Animals

package zoo;

class Animal {
    private String name;

    public String getName() { return name; }

    public Animal(String name) { this.name = name; }

    // overridable by default = "this is my default; children MAY replace it"
    public void makeSound() {
        System.out.println(name + " makes a generic animal sound.");
    }
}

class Dog extends Animal {
    public Dog(String name) { super(name); }

    // @Override = "I am replacing the parent's version"
    @Override
    public void makeSound() {
        System.out.println(getName() + " says: Woof! Woof!");
    }
}

class Cat extends Animal {
    public Cat(String name) { super(name); }

    @Override
    public void makeSound() {
        System.out.println(getName() + " says: Meow~");
    }
}

class Duck extends Animal {
    public Duck(String name) { super(name); }
    // No override — Duck inherits the parent's default sound
}

public class Program {
    public static void main(String[] args) {
        Animal a1 = new Dog("Rex");
        Animal a2 = new Cat("Whiskers");
        Animal a3 = new Duck("Donald");

        a1.makeSound();   // Rex says: Woof! Woof!      <- DOG's version ran!
        a2.makeSound();   // Whiskers says: Meow~       <- CAT's version ran!
        a3.makeSound();   // Donald makes a generic...  <- no override, parent version

        // The magic: the SAME LINE of code behaves differently per object.
        // Java looks at the ACTUAL object at runtime, not the variable's type.
    }
}
Figure 17.1 — For overridable methods, Java checks the actual object at runtime, not the variable's declared type.
🧠 Beginner's Logic Breakdown
  1. Two types in play: the variable's type (Animal — decided at compile time) and the object's actual type (Dog — decided when new ran). For an overridable method, Java waits until runtime, checks the actual object, and runs its version. This lookup is called dynamic dispatch.
  2. Remote-control analogy: an Animal-shaped remote has a "makeSound" button. Point it at a dog — bark. Point it at a cat — meow. Same button, behaviour decided by what's actually in front of it.
  3. Java note: In Java, instance methods are overridable by default (unless final). Always mark replacements with @Override so the compiler verifies you are truly overriding.
  4. Contrast with overloading (Session 11): overloading = same name, different parameters, chosen at compile time. Overriding = same name, same signature, different class, chosen at runtime. Exams love this comparison!

1.2 Calling the Parent Version Too: super.method()

class Puppy extends Dog {
    public Puppy(String name) { super(name); }

    @Override
    public void makeSound() {
        super.makeSound();                          // first do everything Dog does...
        System.out.println(getName() + " also whimpers cutely.");
    }
}
// Output for a Puppy: "Rex says: Woof! Woof!" then "Rex also whimpers cutely."

Use super.method() when the child wants to extend rather than completely replace the parent's behaviour.

1.3 The Trap: Forgetting @Override

class Fox extends Animal {
    public Fox(String name) { super(name); }

    // Typo in the name — this is a NEW method, not an override!
    public void makesound() {   // wrong capitalisation
        System.out.println(getName() + ": Ring-ding-ding!");
    }
}

Fox f = new Fox("Fergus");
f.makesound();               // Ring-ding-ding!      (calls the new method)

Animal a = new Fox("Fergus");
a.makeSound();               // generic animal sound!!! (parent version — no true override)
// Without @Override, the compiler never warned you. Always annotate overrides.
Rule of Thumb

Always put @Override on methods that replace a parent method. If you mistype the name or signature, the compiler errors immediately instead of silently creating a brand-new method that never participates in polymorphism.

Session 17 Summary

  • A child object may live in a parent-typed variable (is-a makes it truthful).
  • overridable (parent permits) + override (child replaces) = runtime polymorphism.
  • For overridable methods, the actual object decides which version runs — dynamic dispatch.
  • super.method() extends instead of replaces; new hides and breaks the promise — avoid.
  • Overloading = compile-time, different parameters. Overriding = runtime, different classes.
