Lesson 08 of 10 — The Third Pillar of OOP

Polymorphism

Greek: poly = many, morph = form. The same method call — animal.makeSound() — produces a bark from a Dog and a meow from a Cat. The caller doesn't need to know or care which one it is talking to. This one idea powers most professional software design.

⏱ 4 Hours Integrated 📋 Session 17 of 23 🏛 Pillar 3 of 4

1. The Setup: A Child in a Parent-Shaped Box

First, a fact that surprises everyone: because a Car is a Vehicle, Java allows this:

Vehicle v = new Car("Toyota", 2022, 4);   // a Car stored in a Vehicle variable — LEGAL!
// Think: a Car parked in a space marked "Vehicles". Perfectly truthful.

v.accelerate();          // fine — Vehicles can accelerate
// v.openBoot();         // ERROR — the variable's TYPE is Vehicle, so only Vehicle
//                          members are visible through it, even though a Car is inside.

Why would we ever do this? Because it lets one variable (or one List!) handle any vehicle — car, bus or bike. But it raises the key question: if the child changed a method, which version runs through the parent-typed variable — the parent's or the child's?

Definition — Polymorphism (Runtime)

Runtime polymorphism lets a derived class provide its own implementation of a base-class method, and guarantees the derived version runs even when the object is accessed through a base-typed variable. Java enables it by default: instance methods are overridable unless marked final. Mark replacements with @Override.

1.1 The Classic Demo — Animals

package zoo;

class Animal {
    private String name;

    public String getName() { return name; }

    public Animal(String name) { this.name = name; }

    // overridable by default = "this is my default; children MAY replace it"
    public void makeSound() {
        System.out.println(name + " makes a generic animal sound.");
    }
}

class Dog extends Animal {
    public Dog(String name) { super(name); }

    // @Override = "I am replacing the parent's version"
    @Override
    public void makeSound() {
        System.out.println(getName() + " says: Woof! Woof!");
    }
}

class Cat extends Animal {
    public Cat(String name) { super(name); }

    @Override
    public void makeSound() {
        System.out.println(getName() + " says: Meow~");
    }
}

class Duck extends Animal {
    public Duck(String name) { super(name); }
    // No override — Duck inherits the parent's default sound
}

public class Program {
    public static void main(String[] args) {
        Animal a1 = new Dog("Rex");
        Animal a2 = new Cat("Whiskers");
        Animal a3 = new Duck("Donald");

        a1.makeSound();   // Rex says: Woof! Woof!      <- DOG's version ran!
        a2.makeSound();   // Whiskers says: Meow~       <- CAT's version ran!
        a3.makeSound();   // Donald makes a generic...  <- no override, parent version

        // The magic: the SAME LINE of code behaves differently per object.
        // Java looks at the ACTUAL object at runtime, not the variable's type.
    }
}
Figure 17.1 — For overridable methods, Java checks the actual object at runtime, not the variable's declared type.
🧠 Beginner's Logic Breakdown
  1. Two types in play: the variable's type (Animal — decided at compile time) and the object's actual type (Dog — decided when new ran). For an overridable method, Java waits until runtime, checks the actual object, and runs its version. This lookup is called dynamic dispatch.
  2. Remote-control analogy: an Animal-shaped remote has a "makeSound" button. Point it at a dog — bark. Point it at a cat — meow. Same button, behaviour decided by what's actually in front of it.
  3. Java note: In Java, instance methods are overridable by default (unless final). Always mark replacements with @Override so the compiler verifies you are truly overriding.
  4. Contrast with overloading (Session 11): overloading = same name, different parameters, chosen at compile time. Overriding = same name, same signature, different class, chosen at runtime. Exams love this comparison!

1.2 Calling the Parent Version Too: super.method()

class Puppy extends Dog {
    public Puppy(String name) { super(name); }

    @Override
    public void makeSound() {
        super.makeSound();                          // first do everything Dog does...
        System.out.println(getName() + " also whimpers cutely.");
    }
}
// Output for a Puppy: "Rex says: Woof! Woof!" then "Rex also whimpers cutely."

Use super.method() when the child wants to extend rather than completely replace the parent's behaviour.

1.3 The Trap: Forgetting @Override

class Fox extends Animal {
    public Fox(String name) { super(name); }

    // Typo in the name — this is a NEW method, not an override!
    public void makesound() {   // wrong capitalisation
        System.out.println(getName() + ": Ring-ding-ding!");
    }
}

Fox f = new Fox("Fergus");
f.makesound();               // Ring-ding-ding!      (calls the new method)

Animal a = new Fox("Fergus");
a.makeSound();               // generic animal sound!!! (parent version — no true override)
// Without @Override, the compiler never warned you. Always annotate overrides.
Rule of Thumb

Always put @Override on methods that replace a parent method. If you mistype the name or signature, the compiler errors immediately instead of silently creating a brand-new method that never participates in polymorphism.

Library System Project – Phase 5: Polymorphic Catalog

Library System  •  Phase 5 of 6

One Catalog to Rule Them All

⏱ 4 Hours 📋 Session 18 of 23 📂 Opens Phase 4 Project 📝 Continuous Assessment Project

1. The Power Move: One List, Many Types

Because every Book and Dvd is a LibraryItem, they can all live in a List<LibraryItem>:

import java.util.*;

List<LibraryItem> catalog = new ArrayList<>();
catalog.add(new Book("Clean Code", "Robert C. Martin", "978-0132350884", 2008));
catalog.add(new Dvd("Inception", "Christopher Nolan", 148));

// ONE loop handles every item — present and FUTURE:
for (LibraryItem item : catalog)
{
    item.printDetails();      // each Object answers with ITS OWN version — dynamic dispatch
}
Key Point — Why Professionals Love This

Add a new class Magazine extends LibraryItem tomorrow and this loop already works with it — zero changes to existing code. Systems designed around polymorphic collections grow by adding classes, not by editing old ones.

Figure 18.1 — One polymorphic list holds every item type; one loop dispatches to each object's override.

1.1 Overriding toString() — Every Object's Business Card

All classes secretly inherit from Object, which has an overridable method toString(). By default it prints the class name — useless. Override it and your objects describe themselves everywhere:

class Book extends LibraryItem
{
    // ... existing code ...

    @Override
    public String toString()          // Object.toString() is overridable — we override it
    {
        return "Book: " + title + " by " + author;
    }
}

Book b = new Book("Clean Code", "Robert C. Martin", "978-0132350884", 2008);
System.out.println(b);          // prints "Book: Clean Code by Robert C. Martin"
                               // println called toString() for us!

1.2 Peeking Inside the Box: instanceof

Occasionally you genuinely need to know what's inside a base-typed variable:

for (LibraryItem item : catalog) {
    if (item instanceof Dvd) {
        Dvd d = (Dvd) item;
        System.out.println("  DVD runtime: " + d.getDurationMinutes() + " minutes");
    }

    if (item instanceof Book) {
        Book b = (Book) item;
        System.out.println("  isbn: " + b.getIsbn());
    }
}
🧠 Beginner's Logic Breakdown
  1. instanceof asks, cast converts: check the actual type first, then cast. (Modern Java also allows pattern matching: if (item instanceof Dvd d).)
  2. Use sparingly! If your loop is full of instanceof-checks, you're fighting polymorphism instead of using it. Better: move the varying behaviour into an overridable method and let dispatch do the work.

2. Library System — Phase 5 Build

The Client's Request — Phase 5

"The staff hate the separate menus for books and DVDs. One list, one search, one borrow flow please. And listings should show the right details for each item type."

Step 1 — Override printDetails Per Child

// In LibraryItem.java — overridable by default; children may @Override
public void printDetails()
{
    String status = isAvailable ? "Available" : "Borrowed";
    System.out.println(title + " | loan " + loanDays + " days | " + status);
}
// In Book.java — extend the base output with book specifics
@Override
public void printDetails()
{
    super.printDetails();                                  // reuse the common line...
    System.out.println("   Book: by " + author + " (" + yearPublished + ") isbn " + isbn);
}

// In Dvd.java
@Override
public void printDetails()
{
    super.printDetails();
    System.out.println("   DVD: directed by " + director + ", " + durationMinutes + " min");
}

Step 2 — Collapse Two Lists into One

// File: Library.java  (Phase 5)
package librarysystem;

import java.util.*;

class Library {
    // ONE list holds Books AND Dvds — they are all LibraryItems
    private List<LibraryItem> catalog = new ArrayList<>();

    public void add(LibraryItem item) {          // one add replaces addBook/addDvd
        catalog.add(item);
    }

    public LibraryItem find(String title) {      // one find works for every type
        for (LibraryItem item : catalog) {
            if (item.getTitle().equalsIgnoreCase(title)) {
                return item;
            }
        }
        return null;
    }

    public void listAll() {
        System.out.println("--- Catalog (" + catalog.size() + " items) ---");
        for (LibraryItem item : catalog) {
            item.printDetails();     // each item prints ITS OWN details — polymorphism!
        }
    }

    public void listAvailable() {
        for (LibraryItem item : catalog) {
            if (item.isAvailable()) {
                item.printDetails();
            }
        }
    }
}
// In Main — seeding is beautifully uniform now:
Library lib = new Library();
lib.add(new Book("Clean Code", "Robert C. Martin", "978-0132350884", 2008));
lib.add(new Dvd("Inception", "Christopher Nolan", 148));

lib.listAll();
// Clean Code | loan 14 days | Available
//    Book: by Robert C. Martin (2008) isbn 978-0132350884
// Inception | loan 3 days | Available
//    DVD: directed by Christopher Nolan, 148 min
Figure 18.2 — Phase 5 collapses duplicate lists and methods into one polymorphic catalog.
🧠 Beginner's Logic Breakdown
  1. Count what disappeared: two lists → one; two Add methods → one; two Find methods → one; two list-menu branches → one. Polymorphism deleted duplicate code while adding the per-type detail printing the client wanted.
  2. The @Override / method overriding pair at work: item.printDetails() in the loop — the variable is LibraryItem-typed, but each actual object (Book/Dvd) supplies its own override. Same line, two behaviours.
  3. super.printDetails() in every override: children extend rather than duplicate the common status line — one source of truth preserved.
  4. Borrowing needed no change at all: Borrow/Return live in the base and work through the base-typed variable — inherited behaviour and polymorphism cooperating.

  • List<LibraryItem> holds every derived type; one loop dispatches to each object's override.
  • overridable printDetails + per-child @Override gives type-specific listings through one call.
  • Override toString() for automatic, meaningful printing everywhere.
