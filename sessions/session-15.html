Lesson 07 of 10 — The Second Pillar of OOP

Inheritance

Look at any real system: a Car, a Bus and a Motorbike share 90% of their behaviour. Copy-pasting that 90% into three classes is a maintenance nightmare. Inheritance lets one class receive everything from another and add only what's different — the family tree of code.

⏱ 3 Hours Integrated 📋 Session 14 of 23 🏛 Pillar 2 of 4

1. The Problem: Sibling Classes Repeating Themselves

// WITHOUT inheritance — painful duplication:
class Car {
    private String brand;
    protected int speed;
    private int numberOfDoors;

    public String getBrand() { return brand; }
    public void setBrand(String brand) { this.brand = brand; }
    public int getSpeed() { return speed; }
    public int getNumberOfDoors() { return numberOfDoors; }
    public void setNumberOfDoors(int numberOfDoors) { this.numberOfDoors = numberOfDoors; }

    public void accelerate() { speed += 10; }          // identical
    public void brake() { speed = 0; }                 // identical
}

class Motorbike {
    private String brand;                              // copy-pasted!
    protected int speed;                                 // copy-pasted!
    private boolean hasSideCar;                        // bike-specific

    public String getBrand() { return brand; }
    public void setBrand(String brand) { this.brand = brand; }
    public int getSpeed() { return speed; }
    public boolean hasSideCar() { return hasSideCar; }
    public void setHasSideCar(boolean hasSideCar) { this.hasSideCar = hasSideCar; }

    public void accelerate() { speed += 10; }          // copy-pasted!
    public void brake() { speed = 0; }                 // copy-pasted!
}
// A bug in accelerate must now be fixed TWICE. Add a Bus? THREE times. This does not scale.
Definition — Inheritance

Inheritance is a mechanism where a class (the derived/child class) automatically receives all non-private members of another class (the base/parent class), and can add its own members on top. In Java, the extends keyword declares it: class Car extends Vehicle reads as "Car is a Vehicle".

The "is-a" Test

Use inheritance only where the sentence "X is a Y" sounds naturally true. A Car is a Vehicle ✓. A Student is a Person ✓. An Engine is a Car? ✗ — an engine is part of a car; that's composition (Lesson 09), not inheritance.

1.1 The Solution — One Parent, Many Children

// File: Vehicle.java — the BASE (parent) class holds everything common
package garage;

class Vehicle {
    private String brand;
    private int year;
    protected int speed;

    public String getBrand() { return brand; }
    public void setBrand(String brand) { this.brand = brand; }
    public int getYear() { return year; }
    public void setYear(int year) { this.year = year; }
    public int getSpeed() { return speed; }

    public void accelerate() {
        speed += 10;
        System.out.println(brand + " is now going " + speed + " km/h");
    }

    public void brake() {
        speed = 0;
        System.out.println(brand + " stopped.");
    }
}
// File: Car.java — "extends" means "Car inherits from Vehicle"
package garage;

class Car extends Vehicle {                     // Car IS A Vehicle
    // Car adds ONLY what makes a car special:
    private int numberOfDoors;

    public int getNumberOfDoors() { return numberOfDoors; }
    public void setNumberOfDoors(int numberOfDoors) { this.numberOfDoors = numberOfDoors; }

    public void openBoot() {
        System.out.println("The " + getBrand() + "'s boot is open.");   // brand is INHERITED
    }
}
// File: Motorbike.java
package garage;

class Motorbike extends Vehicle {
    private boolean hasSideCar;

    public boolean hasSideCar() { return hasSideCar; }
    public void setHasSideCar(boolean hasSideCar) { this.hasSideCar = hasSideCar; }

    public void doWheelie() {
        System.out.println("The " + getBrand() + " pops a wheelie! (Don't try this at home)");
    }
}
// In main — children can use inherited AND own members:
Car car = new Car();
car.setBrand("Toyota");          // inherited — works!
car.setNumberOfDoors(4);         // own field
car.accelerate();                // inherited method  -> "Toyota is now going 10 km/h"
car.openBoot();                  // own method

Motorbike bike = new Motorbike();
bike.setBrand("Bajaj");
bike.accelerate();               // the SAME inherited code — written once, used by all children
bike.doWheelie();

// car.doWheelie();              // COMPILER ERROR — wheelie belongs to Motorbike only
Figure 14.1 — A class hierarchy. The hollow arrow points from child to parent and reads "is a". Common code lives once, at the top.
🧠 Beginner's Logic Breakdown
  1. Read class Car extends Vehicle aloud: "Car is a Vehicle." Everything a Vehicle has, a Car automatically has — without writing it again.
  2. Inside openBoot() we used getBrand() even though Car never declared it — the field/getter arrived through inheritance, as if it were pasted in invisibly.
  3. Inheritance is one-directional: children get the parent's members; the parent knows nothing about its children. Vehicle cannot call doWheelie().
  4. What is NOT inherited: private members exist inside the child object but are inaccessible to the child's code (Session 15 fixes this with protected), and constructors are not inherited (also Session 15).

1.2 Rules of Java Inheritance

  • Single inheritance only: a class may have exactly one direct superclass (class A extends B, C with two classes is illegal in Java — use implements for interfaces).
  • Chains are allowed: ElectricCar extends Car extends Vehicle — ElectricCar inherits from both, transitively.
  • Everything ultimately inherits from Object: the built-in root class of all Java types — this is why every object has toString().
Figure 14.2 — Inheritance chains are allowed. ElectricCar receives members from Car, Vehicle, and object.

Inheritance in Depth – protected, base Constructors

1. protected — The Family-Only Modifier

Session 14 left a problem: if Vehicle's Speed has a private set, how can a child like SportsCar implement its own turboBoost() that changes the speed? private locks children out too. Making it public exposes it to everyone. The middle ground:

Definition — protected

A protected member is accessible inside its own class and inside any derived class, but not from outside the family. It sits between private (self only) and public (everyone).

Figure 15.1 — Three circles of trust: private (my room), protected (family), public (street).
class Vehicle {
    private String brand;
    protected int speed;                 // protected: children may touch it, outsiders may not

    public String getBrand() { return brand; }
    public void setBrand(String brand) { this.brand = brand; }
    public int getSpeed() { return speed; }   // public read-only window for outsiders

    public void accelerate() {
        speed += 10;
    }
}

class SportsCar extends Vehicle {
    public void turboBoost() {
        speed += 50;                         // LEGAL — SportsCar is family
        System.out.println(getBrand() + " turbo! Now at " + speed + " km/h");
    }
}

// In main:
SportsCar f = new SportsCar();
f.setBrand("Ferrari");
f.turboBoost();          // works — the child manipulated the protected field
// f.speed = 999;        // COMPILER ERROR — main is not part of the family
🧠 Beginner's Logic Breakdown
  1. Three circles of trust: private = my room only; protected = family house; public = the street. speed lives in the family house: Vehicle and all its descendants may enter, strangers (Main) may not.
  2. Encapsulation is preserved: outsiders still cannot corrupt speed — they read it through the public getter but change it only via public methods (accelerate) or family logic (turboBoost).
  3. Use sparingly: protected is a bigger door than private. Prefer private + protected methods when only behaviour (not raw data) needs sharing.

2. Constructors in a Hierarchy — super(...)

Constructors are not inherited. If Vehicle demands (brand, year) at birth, each child must arrange for those values to reach Vehicle's constructor. The keyword super does it:

class Vehicle {
    private String brand;
    private int year;

    public String getBrand() { return brand; }
    public int getYear() { return year; }

    public Vehicle(String brand, int year) {          // parent constructor demands the essentials
        this.brand = brand;
        this.year = year;
        System.out.println("1) Vehicle constructor ran");
    }
}

class Car extends Vehicle {
    private int numberOfDoors;

    public int getNumberOfDoors() { return numberOfDoors; }

    // super(brand, year) forwards values UP to the Vehicle constructor
    public Car(String brand, int year, int doors) {
        super(brand, year);
        this.numberOfDoors = doors;                       // then the child adds its own part
        System.out.println("2) Car constructor ran");
    }
}

// In main:
Car c = new Car("Toyota", 2022, 4);
// Output order:
// 1) Vehicle constructor ran      <- parent part built FIRST
// 2) Car constructor ran          <- then the child part
🧠 Beginner's Logic Breakdown
  1. Bottom floor first: a Car object contains a complete Vehicle "inside" it. Construction is like building a house: foundation (Vehicle) before walls (Car). Hence the output order — always parent first.
  2. super(brand, year) is the delivery van carrying the child's constructor arguments up to the parent's constructor. Compare with this(...) from Session 11 which chains sideways within the same class; super(...) chains upwards.
  3. When can you omit it? Only if the parent has a parameterless constructor — Java then calls it silently. If the parent demands parameters, forgetting super(...) is a compiler error.

2.1 A Three-Level Chain

class ElectricCar extends Car {
    private int batteryCapacity;

    public int getBatteryCapacity() { return batteryCapacity; }

    public ElectricCar(String brand, int year, int doors, int battery) {
        super(brand, year, doors);                 // passes to Car, which passes to Vehicle
        this.batteryCapacity = battery;
        System.out.println("3) ElectricCar constructor ran");
    }
}

// new ElectricCar("Tesla", 2024, 4, 75) prints 1) then 2) then 3) — the full chain, top down.
Figure 15.2 — Constructor execution order: always parent first, then child, down the chain.

2.2 Hierarchy Design Guidelines

  • Pull up what is shared by all children; keep down what only some have.
  • Keep it shallow: 2–3 levels is usually plenty. Deep towers become impossible to reason about.
  • Re-run the is-a test at every level: ElectricCar is a Car ✓, Car is a Vehicle ✓.
  • Don't inherit for convenience: shared data shape is not shared identity.

Session 15 Summary

  • protected = family-only access: the class and all its descendants.
  • Constructors are not inherited; super(args) forwards values to the parent constructor.
  • Construction order: always parent first, down the chain to the newest child.
  • Pull shared members up, keep hierarchies shallow, verify is-a at each level.
