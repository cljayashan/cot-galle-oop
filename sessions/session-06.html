Why We Need a New Way to Think About Programs

You can draw a perfect flowchart for "borrow a book from the library." But when the system grows — members, fines, DVDs, staff logins — a single long list of steps becomes impossible to maintain. Object-Oriented Programming (OOP) organises code the way we organise the real world: as interacting objects.

1. What You Already Know — Procedural Thinking

In your Programming Logic module you solved problems as a sequence of steps:

  1. Get input from the user
  2. Process (calculate, decide)
  3. Output the result

This is called procedural programming. The program is one long recipe. Data (variables) and actions (steps) are separate. For small problems — calculate rectangle area, check vowels — this works beautifully.

Definition

Procedural programming focuses on what happens step by step. You write functions or blocks of code that operate on data stored in variables. The flowchart is the blueprint.

Figure 1.1 — In procedural style, data floats in one big program and many functions touch it.

2. The Object-Oriented View

Look around your classroom. You see objects: desks, students, teachers, whiteboards. Each object has:

  • Properties (attributes) — a desk has four legs, a colour
  • Behaviours (methods) — a student can sit, read, answer a question

OOP models software the same way. A Book object knows its own title and ISBN. A Member object knows its name and can borrow a book. Programs become a society of objects sending messages to each other, not one giant list of steps.

Definition

Object-Oriented Programming (OOP) organises software as objects that combine data and behaviour. Objects interact by calling each other's methods. Large systems are built by combining many small, focused objects.

Figure 1.2 — OOP: data lives inside the object that owns it. Methods define what each object can do.

3. The Four Pillars of OOP (Roadmap)

You will study each pillar in depth later. For now, know the names and one-line meanings:

1. Encapsulation

Hide internal data; expose only safe methods (like an ATM — you cannot open the vault).

2. Inheritance

Reuse code — a Dvd is a LibraryItem and inherits common fields.

3. Polymorphism

One method name, many behaviours — getInfo() prints different text for Book vs Dvd.

4. Abstraction

Hide complexity — define Lendable without caring whether it is a book or equipment.

Exam tip

Memorise the four pillars with the mnemonic E-I-P-A. Every pillar will appear in the Library System project across Block 2.

4. Why Java?

Java was designed for Object-Oriented Programming and runs on the JVM (Java Virtual Machine). It is used in:

  • Enterprise business software (banks, hospitals)
  • Web applications (Spring / Jakarta EE)
  • Android mobile apps
  • Desktop and server tools across many industries

In this module we use console applications — text-based programs in the terminal — so you focus on OOP concepts without UI complexity.

Discussion Lab (No Code Yet)
  1. Pick a system you know: school canteen, online shop, or hospital reception.
  2. List five objects you would model (nouns).
  3. For each object, write two properties and one behaviour.
  4. Draw arrows: which object talks to which? (e.g. Student orders from Canteen)
  5. Compare with a partner: did you choose the same objects?

Session Summary

  • Procedural = steps + shared variables; OOP = objects with data + behaviour
  • OOP matches real-world entities and scales to large systems
  • Four pillars: Encapsulation, Inheritance, Polymorphism, Abstraction
