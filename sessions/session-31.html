Lesson 09 of 10 — The Fourth Pillar of OOP

Abstraction

Does it make sense to create new LibraryItem("???") — an item that is neither book, magazine nor DVD? No! Some classes exist only as concepts for others to build on. Abstraction lets us say so in code — and lets us define pure contracts that unrelated classes can promise to fulfil.

⏱ 3 Hours Theory + Practical 📚 Pillar 4 of 4 🔗 Leads to Library Phase 6

1. What Is Abstraction?

So far you have built concrete classes — Book, Car, Member — that you can instantiate directly. But some ideas in a system are incomplete by nature. There is no such thing as a generic "Shape" sitting in the real world, only circles and rectangles. There is no plain "Library Item" on a shelf, only books and DVDs. Abstraction is how we express that incompleteness in Java.

Definition — Abstraction

Abstraction means exposing only the essential concept of something while hiding implementation details. In Java it has two tools: the abstract class (a partially-built base that cannot be instantiated) and the interface (a pure contract with no implementation at all).

Figure 19.1 — Abstraction is the fourth OOP pillar. It works with inheritance and polymorphism to define incomplete families and cross-family contracts.

2. Abstract Classes — Concepts You Cannot Instantiate

An abstract class is a class marked with the abstract keyword. You cannot write new Shape() or new LibraryItem("x") — the compiler refuses. The class exists solely as a blueprint for derived classes.

package shapes;

import java.util.*;

// 'abstract' on the class = "you cannot 'new' me - I exist only to be inherited"
abstract class Shape {
    private String name;

    public String getName() { return name; }

    public Shape(String name) { this.name = name; }

    // ABSTRACT METHOD: signature only, NO body. Every child MUST override it.
    public abstract double area();

    // CONCRETE METHOD: shared implementation inherited as usual.
    // It calls area() even though area has no body here — children supply it.
    public void describe() {
        System.out.println(name + " has area " + String.format("%.2f", area()));
    }
}

class Circle extends Shape {
    private double radius;

    public double getRadius() { return radius; }

    public Circle(double radius) {
        super("Circle");
        this.radius = radius;
    }

    @Override
    public double area() {               // forced by the compiler!
        return Math.PI * radius * radius;
    }
}

class Rectangle extends Shape {
    private double length;
    private double width;

    public double getLength() { return length; }
    public double getWidth() { return width; }

    public Rectangle(double l, double w) {
        super("Rectangle");
        this.length = l;
        this.width = w;
    }

    @Override
    public double area() {
        return length * width;
    }
}

public class Program {
    public static void main(String[] args) {
        // Shape s = new Shape("???");   // COMPILER ERROR - cannot instantiate abstract class

        List<Shape> shapes = new ArrayList<>();
        shapes.add(new Circle(5));
        shapes.add(new Rectangle(4, 6));

        for (Shape s : shapes) {
            s.describe();       // Circle has area 78.54 / Rectangle has area 24.00
        }
    }
}
Figure 19.2 — UML-style abstract class hierarchy. Shape is a concept; Circle and Rectangle are concrete.
🧠 Beginner's Logic Breakdown
  1. Abstract class = incomplete blueprint: Shape says "every shape has a Name and can Describe itself, and every shape HAS an area — but I cannot tell you how to compute it; that's each child's job."
  2. abstract method vs overridable concrete method: A concrete method with a body can be overridden (optional). abstract = "no default exists, you MUST provide one" (compiler-enforced). Mark overrides with @Override.
  3. The template pattern: concrete describe() calls abstract area() — the parent defines the skeleton of behaviour, children plug in the varying step.
  4. Library connection: our LibraryItem should have been abstract all along — there is no such thing as a plain "library item"! We fix that in Phase 6 (Session 20).

2.1 Rules for Abstract Classes

  • An abstract class can have constructors, fields, getters/setters, and concrete methods.
  • An abstract class cannot be instantiated with new.
  • If a class contains even one abstract member, the class itself must be declared abstract.
  • A non-abstract (concrete) child must override every inherited abstract member, or it too must be abstract.

3. Interfaces — Pure Contracts

Definition — Interface

An interface declares a set of members (methods (and getters)) with no implementation and no fields — a pure contract. A class that implements the interface promises to provide every member. Naming convention: interfaces are adjectives/capabilities (Printable, Lendable). A class may implement any number of interfaces.

import java.util.*;

// An interface: WHAT must be doable - never HOW
interface Playable {
    void play();                       // no body; interface methods are public
    void stop();
    int getDurationMinutes();
}

interface Downloadable {
    void download(String folder);
}

// A class implements interfaces with the 'implements' keyword
class Song implements Playable, Downloadable {            // TWO interfaces at once - legal!
    private String title;
    private int durationMinutes;

    public String getTitle() { return title; }
    public int getDurationMinutes() { return durationMinutes; }

    public Song(String title, int duration) {
        this.title = title;
        this.durationMinutes = duration;
    }

    public void play()  { System.out.println("▶ Playing " + title); }
    public void stop()  { System.out.println("Stopped " + title); }
    public void download(String folder) { System.out.println("Saving " + title + " to " + folder); }
}

class Movie implements Playable {                         // unrelated to Song - still playable
    private String title;
    private int durationMinutes;

    public String getTitle() { return title; }
    public int getDurationMinutes() { return durationMinutes; }

    public Movie(String title, int duration) {
        this.title = title;
        this.durationMinutes = duration;
    }

    public void play() { System.out.println("🎬 Showing " + title); }
    public void stop() { System.out.println("Paused " + title); }
}

class MediaCenter {
    public void playAll(List<Playable> playlist) {     // interface used as a TYPE
        for (Playable p : playlist) {
            p.play();
        }
    }
}
Figure 19.3 — Inheritance models family (is-a); interfaces model capability (can-do) across unrelated classes. Dotted line with hollow arrow = implements.
🧠 Beginner's Logic Breakdown
  1. Contract analogy: a driving licence doesn't care if you're a teacher or a doctor — it certifies you can drive. Playable certifies a class can Play and Stop, whatever else it is.
  2. Interface as a variable type: List<Playable> accepts anything that signed the contract — polymorphism across family trees.
  3. Why multiple interfaces are safe while multiple base classes are banned: interfaces carry no fields or method bodies, so there is nothing to clash.
  4. Preview for Session 20: Lendable will let Books and standalone Equipment share one lending loop even though Equipment is not a LibraryItem.

Rule of Thumb

Shared code and a true family → abstract class. Shared capability across unrelated classes → interface. Often you use both: class Book extends LibraryItem implements Lendable — one superclass, then interfaces, in that order.

Session 19 Summary

  • Abstract class = partially built base; cannot be instantiated; abstract members MUST be overridden.
  • Template pattern: concrete base methods call abstract ones children must supply.
  • Interface = pure contract ("can-do"); no fields, no bodies; implement as many as needed.
  • Abstract class for is-a + shared code; interface for capabilities across unrelated classes.
  • Syntax: class Book extends LibraryItem implements Lendable — one superclass, then interfaces.

Lesson 10 of 10 — Block 3: Advanced Relationships

Association, Aggregation & Composition

Inheritance ("is-a") is only one way objects relate. Far more common in real systems is "has-a" and "uses-a": a Teacher teaches in a Classroom, a Classroom has Students, a Classroom contains Desks that are destroyed when the room is demolished. This lesson gives you the vocabulary — and the Java patterns — for connecting objects correctly.

⏱ 5 Hours Theory + Practical 📅 Sessions 21 – 23 🏫 The School Project

1. Beyond Inheritance — Why Relationships Matter

In Lessons 06–08 you mastered inheritance — the "is-a" relationship. A Book is a LibraryItem. But not every connection is inheritance. A Teacher is not a Classroom. A Desk is not a Student. These are has-a and uses-a connections — and getting them wrong leads to bugs that inheritance cannot fix.

Definition — Object Relationship

An object relationship exists when one class holds a reference to an object of another class (a field or property pointing at another object). The three standard types — association, aggregation, composition — differ in strength, ownership, and lifetime.

The "is-a" vs "has-a" Test

Before writing code, ask: "Is X a type of Y?" → inheritance. "Does X use/have/contain Y?" → association, aggregation, or composition. Never inherit just to reuse a field — that is a relationship mistake.

2. The Relationship Spectrum

All three relationships mean "objects know about each other" — what differs is ownership and lifetime. Think of them as increasingly strong bonds:

Figure 21.1 — The three relationships in UML style: plain arrow = association, hollow diamond = aggregation, filled diamond = composition (diamond sits on the owner).

2.1 Association — "uses-a / works-with"

Definition — Association

An association is a loose relationship where one object simply knows about (holds a reference to) another. Both objects have completely independent lifetimes. Example: a Teacher is assigned to a Classroom; delete either and the other continues to exist.

class Teacher {
    private String name;
    private Classroom assignedRoom;   // ASSOCIATION: reference to a Classroom created ELSEWHERE

    public String getName() { return name; }
    public Classroom getAssignedRoom() { return assignedRoom; }
    public void setAssignedRoom(Classroom assignedRoom) { this.assignedRoom = assignedRoom; }

    public Teacher(String name) { this.name = name; }

    public void teach() {
        if (assignedRoom == null) {
            System.out.println(name + " has no classroom assigned yet.");
            return;
        }
        System.out.println(name + " is teaching in room " + assignedRoom.getRoomNumber() + ".");
    }
}

// In main - the two objects are created independently and then LINKED:
Classroom r12 = new Classroom("R12");
Teacher silva = new Teacher("Mr. Silva");
silva.setAssignedRoom(r12);         // link
silva.teach();
silva.setAssignedRoom(null);        // unlink - BOTH objects still perfectly alive

2.2 Aggregation — "has-a" (shared, detachable parts)

Definition — Aggregation

Aggregation is a whole–part relationship where the whole has a collection of parts, but the parts are created outside and can outlive the whole or move to another whole. Example: a Classroom has Students — but students exist before the room is assigned and survive if the room closes.

import java.util.*;

class Classroom {
    private String roomNumber; // AGGREGATION: the room HOLDS students but did not CREATE them
    private List<Student> students = new ArrayList<>();

    public String getRoomNumber() { return roomNumber; }

    public Classroom(String roomNumber) { this.roomNumber = roomNumber; }

    public void enroll(Student s) {         // parts are handed IN from outside
        students.add(s);
    }

    public void remove(Student s) {         // ...and can leave again, unharmed
        students.remove(s);
    }
}

// In main:
Student amara = new Student("Amara");     // student exists FIRST, independently
Classroom r12 = new Classroom("R12");
r12.enroll(amara);                        // aggregated into the room
Classroom r15 = new Classroom("R15");
r12.remove(amara);
r15.enroll(amara);                        // same student moved - fine!

2.3 Composition — "part-of" (owned, lives and dies with)

Definition — Composition

Composition is the strongest whole–part relationship: the whole creates and owns its parts. Parts cannot be shared with another whole and cannot exist independently — when the whole dies, the parts die with it. Example: a Classroom is composed of Desks; when the classroom is destroyed, its desks are destroyed too.

import java.util.*;

class Desk {
    private int deskNumber;

    public int getDeskNumber() { return deskNumber; }

    public Desk(int number) { this.deskNumber = number; }
}

class Classroom {
    private String roomNumber; // COMPOSITION: the room CREATES its own desks INSIDE itself.
    private List<Desk> desks = new ArrayList<>();

    public String getRoomNumber() { return roomNumber; }

    public Classroom(String roomNumber, int deskCount) {
        this.roomNumber = roomNumber;
        for (int i = 1; i <= deskCount; i++) {
            desks.add(new Desk(i));       // born inside the constructor - never handed in
        }
    }

    // NO public add/remove for desks, and no getter that exposes the list itself.
    public int getDeskCount() { return desks.size(); }
}

// In main:
Classroom r12 = new Classroom("R12", 30);   // 30 desks spring into existence inside
System.out.println(r12.getDeskCount());            // 30
// When r12 becomes unreachable, its desks are unreachable too -
// the Garbage Collector reclaims the WHOLE with all its PARTS.
Figure 21.2 — Complete School system relationships: Teacher uses Classroom; Classroom has Students; Classroom has Desks (composition).
🧠 Beginner's Logic Breakdown
  1. Look WHERE the part is created — that's the giveaway. Association/aggregation: the part is created outside and a reference is passed in. Composition: the part is created inside the whole (usually in its constructor) and never leaves.
  2. Lifetime test: "If the whole is deleted, does the part survive?" Student — yes → aggregation. Desk — no → composition.
  3. Sharing test: "Can two wholes share one part?" One student in two classrooms at once — no (business rule). One desk in two rooms — impossible → composition.
  4. Memory view (Lesson 05 callback): in composition the only references to Desks live inside the Classroom object — when the room becomes garbage, the desks automatically become unreachable garbage too.

Session 21 Summary

  • Association = knows/uses; both independent; link and unlink freely.
  • Aggregation = has-a; parts handed in from outside, can move or outlive the whole.
  • Composition = part-of; parts born inside the whole, never shared, die with it.
  • Giveaways: where is the part created? can it be reached/shared from outside? who controls its life?
  • Teacher uses Classroom; Classroom has Students; Classroom has Desks — the School project applies all three.
