Memory & Object Lifecycle

Where does an object actually live when you write new Book(...)? Why can two variables change the same data? And who cleans up objects nobody uses anymore? Today we look under the hood of the JVM — and several confusing bugs from earlier sessions suddenly make sense.

⏱ 4 Hours Integrated 📋 Session 13 of 23 🔍 Explains the "weird" bugs

1. Two Places to Live: Stack and Heap

When your Java console program runs, the JVM organises its memory into two main regions with very different personalities:

The StackThe Heap
AnalogyA neat pile of trays — take only from the topA big warehouse with numbered shelves
StoresLocal variables, method parameters, "which method am I in"Objects created with new
SpeedExtremely fastFast, but managed
CleanupAutomatic and instant — a method's tray is thrown away the moment the method returnsBy the Garbage Collector, when objects become unreachable
SizeSmall (about 1 MB per thread)Large (limited by RAM)
Figure 13.1 — The variable b on the stack holds only an address pointing to the real Book object on the heap.
Definition — Value Types vs Reference Types

Primitive types (int, double, boolean, char, …) store their data directly in the variable. Reference types (all class objects, String, arrays, List<T>) store the data on the heap; the variable holds only a reference (memory address) to it.

1.1 The Copy Experiment — Where Bugs Are Born

package memorylab;

public class Program {
    public static void main(String[] args) {
        // ---------- PRIMITIVE: copying copies the DATA ----------
        int a = 10;
        int b = a;          // b receives its own, independent copy of 10
        b = 99;
        System.out.println(a);   // 10  — 'a' is untouched. Two separate boxes.

        // ---------- REFERENCE TYPE: copying copies the ADDRESS ----------
        Book book1 = new Book("Clean Code", "Martin", "111");
        Book book2 = book1;      // copies only the ADDRESS — both point to the SAME object!
        book2.setTitle("HACKED");
        System.out.println(book1.getTitle());   // "HACKED"!!! — there is only ONE Book
                                                // book1 and book2 are two remote controls for one TV
    }
}

class Book {
    private String title;
    private String author;
    private String isbn;

    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public String getAuthor() { return author; }
    public void setAuthor(String author) { this.author = author; }
    public String getIsbn() { return isbn; }
    public void setIsbn(String isbn) { this.isbn = isbn; }

    public Book(String title, String author, String isbn) {
        this.title = title;
        this.author = author;
        this.isbn = isbn;
    }
}
🧠 Beginner's Logic Breakdown
  1. Two boxes vs one TV, two remotes: value assignment duplicates the contents of a box. Reference assignment duplicates only the remote control; the TV (heap object) stays singular. Press a button on either remote and the same TV changes.
  2. This explains Session 09: when we passed a Book into member.borrowBook(book), the method received a copy of the address — so book.borrow() inside the method changed the one true Book that Main also sees. That was exactly what we wanted!
  3. Equality warning: for reference types, book1 == book2 asks "same address?", not "same contents?". Two different Books with identical titles are NOT ==.

1.2 null in Memory Terms

null simply means: this reference variable holds no address — it points at nothing. Calling anything on it (b.getTitle() when b is null) asks the computer to visit "address nothing" → the famous NullPointerException. Now you know why our Library search code always checks if (found == null) first.

2. The Object Lifecycle and the Garbage Collector

Every heap object goes through the same life story:

  1. Birth: new Book(...) — the JVM reserves heap space, zeroes it, runs the constructor, returns the address.
  2. Life: the object serves requests through its methods as long as at least one reference points to it.
  3. Abandonment: the last reference disappears (variable set to null, goes out of scope, or gets overwritten). The object still occupies memory but is unreachable — nobody can ever use it again.
  4. Collection: the Garbage Collector eventually notices, reclaims the memory, and the space is reused for new objects.
Definition — Garbage Collector (GC)

The Garbage Collector is a background service of the JVM that automatically finds heap objects no longer reachable from any live reference and reclaims their memory. Programmers in Java never manually free object memory (unlike C/C++ where forgetting to free causes memory leaks).

Figure 13.2 — The GC keeps whatever it can reach from live references and reclaims the rest. Book B has no arrows pointing to it → collected.

2.1 How the GC Decides (Simple Version)

  • Mark: start from all live variables (stack, static fields) and follow every reference, marking each object reached.
  • Sweep: anything unmarked is garbage — reclaim it.
  • Compact: slide surviving objects together so free memory forms one clean block.
  • Generations trick: the JVM sorts objects by age (Gen 0 = newborn, Gen 2 = old-timers). Most objects die young, so the GC checks Gen 0 very often and cheaply.
Key Point — What This Means for You

You never "delete" objects in Java. To let something go, simply stop referencing it (remove from lists, let variables go out of scope). And never worry about creating short-lived objects — the GC is optimised for exactly that pattern.

Common Misconceptions
  • "Setting a variable to null deletes the object." — No. It removes one reference. If others exist, the object lives on.
  • "The GC runs at fixed times." — No. It runs when needed (memory pressure), automatically.
  • "Java can't leak memory." — Mostly true for pure objects, but keeping references you no longer need (e.g. an ever-growing List) still bloats memory.

3. Lab Time — Watching Memory Behave

🔬 Lab Task 13.1 — The Two Remotes Experiment (40 min)
  1. Create project MemoryLab. Write a simple Person class (private name field, getters/setters, constructor).
  2. Reproduce the copy experiment: int copy vs Person copy. Print results and write one sentence explaining each.
  3. Write static void Rename(Person p) that sets p.setName("Changed"); — call it from Main and print the name after. Explain why Main's object changed although Rename had "only a parameter".
  4. Write static void Replace(Person p) { p = new Person("Brand New"); } — call it and print. The original is unchanged! Explain: the parameter held a copy of the address; pointing that copy elsewhere does not affect Main's variable.
🔬 Lab Task 13.2 — Making Garbage (40 min)
  1. In a loop, create 1,000,000 Person objects without storing them: for (int i = 0; i < 1000000; i++) { Person p = new Person("temp" + i); }
  2. While debugging, use the debugger Variables view and Debug Console in VS Code. Optionally print used memory (next step) to observe GC behaviour.
  3. Print used memory via Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory() before and after the loop, and after calling System.gc() (for observation only — never call this in real programs!).
  4. Answer in your lab book: why doesn't the program run out of memory even though we created a million objects?
🔬 Lab Task 13.3 — Null Detective (25 min)
  1. Write code that deliberately causes a NullPointerException (declare a Person variable without new, call a method on it).
  2. Run with the VS Code debugger (F5). Study the exception: which line, which variable?
  3. Fix it two ways: (a) construct the object, (b) guard with if (p != null).

Session 13 Summary

  • Stack = fast, per-method, auto-cleaned; heap = big warehouse where all new objects live.
  • Value types copy data; reference types copy the address — two remotes, one TV.
  • Passing an object to a method passes the address: the method can change the caller's object.
  • null = points at nothing; using it throws NullPointerException.
  • The GC marks reachable objects, sweeps the rest, compacts survivors — no manual deletion in Java.
  • Objects die when the last reference is gone; the GC is optimised for short-lived objects.
