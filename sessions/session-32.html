1. Final Requirements

The Client's Request — Phase 6 (final)

"Two last things: (1) audit found staff accidentally created 'blank items' that were neither books nor magazines — please make that impossible; (2) at closing time we need one lending status report covering every lendable thing in the building — books, DVDs, and standalone equipment like projectors that aren't catalog items but can still be signed out."

Translation: (1) LibraryItem must become abstract. (2) We need a lending contract that both LibraryItem children and standalone Equipment can fulfil — but Equipment is not a LibraryItem! Unrelated classes sharing a capability = interface (Lendable).

Step 1 — The Lendable Interface

// File: Lendable.java  (NEW)
package librarysystem;

// The LENDING CONTRACT: anything lendable can be signed out and returned.
interface Lendable {
    String getTitle();
    boolean isAvailable();
    boolean lend();              // sign out — returns false if already out
    void returnItem();           // sign back in
}

Step 2 — LibraryItem Becomes Abstract and Implements Lendable

// File: LibraryItem.java  (Phase 6)
package librarysystem;

import java.time.LocalDate;

// abstract: 'new LibraryItem(...)' is now a compiler error - concept only!
abstract class LibraryItem implements Lendable {
    private String title;
    private boolean isAvailable = true;
    protected int loanDays = 14;

    public String getTitle() { return title; }
    public boolean isAvailable() { return isAvailable; }
    public int getLoanDays() { return loanDays; }

    public LibraryItem(String title) {     // abstract classes CAN have constructors
        this.title = title;
    }

    // Lendable.lend() — maps to our existing borrow logic
    public boolean lend() {
        if (!isAvailable) {
            System.out.println("'" + title + "' is already on loan.");
            return false;
        }
        isAvailable = false;
        System.out.println("Lent '" + title + "' — due " + LocalDate.now().plusDays(loanDays));
        return true;
    }

    public void returnItem() {
        if (isAvailable) {
            System.out.println("'" + title + "' was not on loan.");
            return;
        }
        isAvailable = true;
        System.out.println("'" + title + "' returned.");
    }

    // Keep borrow as a convenience alias if Phase 5 code uses it:
    public boolean borrow() { return lend(); }

    // ABSTRACT: every item type MUST describe itself
    public abstract void printDetails();
}

Step 3 — Equipment (NOT a LibraryItem, but IS Lendable)

// File: Equipment.java  (NEW — standalone class, no inheritance from LibraryItem)
package librarysystem;

class Equipment implements Lendable {
    private String title;       // e.g. "Projector #3"
    private boolean isAvailable = true;
    private String location;

    public String getTitle() { return title; }
    public boolean isAvailable() { return isAvailable; }
    public String getLocation() { return location; }

    public Equipment(String title, String location) {
        this.title = title;
        this.location = location;
    }

    public boolean lend() {
        if (!isAvailable) {
            System.out.println("Equipment '" + title + "' is already signed out.");
            return false;
        }
        isAvailable = false;
        System.out.println("Equipment '" + title + "' signed out from " + location + ".");
        return true;
    }

    public void returnItem() {
        if (isAvailable) {
            System.out.println("Equipment '" + title + "' was not signed out.");
            return;
        }
        isAvailable = true;
        System.out.println("Equipment '" + title + "' returned to " + location + ".");
    }
}

🧠 Beginner's Logic Breakdown
  1. Why abstract fixed the audit problem: "blank items" were possible because LibraryItem was a normal class. One keyword later, the compiler guarantees only real item types can be created.
  2. printDetails went abstract: in Phase 5 children could override it; now they must. Add a new item type and forget printDetails? The compiler stops you.
  3. Lendable bridged two families: Book and Projector share no ancestor, yet both appear in one report loop through List<Lendable>. This is exactly what interfaces are for.
  4. Equipment proves the point: you cannot put Equipment in List<LibraryItem> — it isn't one. But you CAN put it in List<Lendable> because it signed the lending contract.
