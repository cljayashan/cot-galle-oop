Classes & Objects

Until now you drew flowcharts and wrote short procedural Java in one file. 1. Class vs Object — From Flowcharts to Blueprints

In Session 03 you turned a Rectangle flowchart into Java where variables lived in Main. That works for tiny programs, but real software models many things at once — cars, accounts, books. OOP gives each "thing" its own bundle of data. The vocabulary starts here.

Definition — Class

A class is a blueprint or template that describes what attributes (data) and methods (behaviour) a certain kind of object will have. A class does not hold real data in memory by itself — it is only the design, like an empty registration form before anyone fills it in.

Definition — Object (Instance)

An object is a concrete instance of a class, created with the new keyword. Each object gets its own copy of the fields in memory. Creating an object is called instantiation.

Bridge from Flowcharts

Think of a class as the legend on your flowchart that defines what a "Vehicle" box can store. Each object is one actual box on the diagram with real values written inside it.

2. Fields — The Object's Memory

Definition — Field (Attribute)

A field is a variable declared directly inside a class (outside any method). It stores the state/data of each object. In OOP theory fields are called attributes; Java programmers usually say fields.

Designing fields is a modelling exercise: "What must every Vehicle remember about itself?" Compare with Session 02 where width and height were local variables in Main — now they live inside the object so they survive between method calls.

Figure 2.2 — Each object owns its own field values. Method code is shared; data is not.

Create the Vehicle class in a separate file (in Explorer: New File → name it Vehicle.java):

// File: Vehicle.java
// One class per file keeps projects organised — professional habit from day one.

    class Vehicle
    {
        // ================= FIELDS (attributes) =================
        // Declared inside the class, OUTSIDE any method.
        // Every Vehicle object gets its own copy of each field.

        public String Brand;        // e.g. "Toyota"
        public String Model;        // e.g. "Corolla"
        public int Year;            // e.g. 2020
        public double FuelLevel;    // litres currently in the tank
        public int Speed;           // current speed in km/h

        // ================= METHODS (behaviour) =================

        public void accelerate()
        {
            Speed = Speed + 10;                 // increase this object's own speed
            FuelLevel = FuelLevel - 0.5;        // accelerating burns fuel
            System.out.println(Brand + " accelerates to " + Speed + " km/h. Fuel left: " + FuelLevel + " L");
        }

        public void brake()
        {
            this.speed = 0;                          // stop this vehicle
            System.out.println(Brand + " has stopped.");
        }

        public void describe()
        {
            System.out.println(Year + " " + Brand + " " + Model + " | Speed: " + Speed + " km/h | Fuel: " + FuelLevel + " L");
        }
    }

And the program that uses it (this stays in Main.java):

// File: Main.java

    public class Main
    {
        public static void main(String[] args)
        {
            // Instantiate two independent vehicles from the same blueprint
            Vehicle car = new Vehicle();
            car.Brand = "Toyota";
            car.Model = "Corolla";
            car.Year  = 2020;
            car.FuelLevel = 40;
            car.this.speed = 0;

            Vehicle bus = new Vehicle();
            bus.Brand = "Lanka Ashok Leyland";
            bus.Model = "Viking";
            bus.Year  = 2018;
            bus.FuelLevel = 90;
            bus.this.speed = 0;

            // Each object acts on ITS OWN data
            car.describe();
            bus.describe();

            car.accelerate();     // only the car speeds up
            car.accelerate();     // car is now at 20 km/h
            bus.describe();       // bus is still at 0 km/h — unaffected!

            car.brake();
            // pause: new java.util.Scanner(System.in).nextLine();
        }
    }
🧠 Beginner's Logic Breakdown
  1. Two files, one program: VS Code (Extension Pack for Java) compiles every .java file in the folder together. Main.java can see Vehicle.java because they are in the same package (or the default package).
  2. Fields live outside methods: Speed is declared at class level, so it survives between method calls. A variable declared inside a method is destroyed when the method ends — like a flowchart box that exists only inside one process block.
  3. Trace the flow: read Main top to bottom like a flowchart. When we call car.accelerate(), the line Speed = Speed + 10; means "the speed of car". When we later call bus.describe(), bus's Speed is still 0 — proof that each object owns separate data.
  4. new Vehicle(): asks the runtime to allocate memory for a new object and return a reference (label) you store in car or bus.
Common Beginner Errors
  • Forgetting new: writing Vehicle car; then car.Brand = "Toyota"; crashes — you declared a label but never built the object. Always Vehicle car = new Vehicle();
  • Confusing class and object: Vehicle.accelerate() is wrong — you must call the method on an object: car.accelerate().
  • Fields declared inside Main: then they are just local variables, not part of the object. Fields go directly inside the class body.
  • Wrong file: putting the class inside Main.java works for tiny demos but hides the habit of one class per file. Start correctly now.

3. Designing Your Own Classes — The Noun/Verb Method

A reliable recipe for turning a problem description into a class design — the same thinking you used when naming boxes in a flowchart:

  1. Read the problem and underline the nouns. "A student enrols in a course and receives a grade." → candidate classes: Student, Course, Grade.
  2. For each noun, ask: what must it remember? → fields with types. Student: Name (String), IndexNumber (String), Average (double).
  3. Circle the verbs connected to each noun. "enrols", "calculates average" → methods: enroll(), calculateAverage().
  4. Write the class skeleton — fields first, then empty methods, then fill in method bodies one at a time, testing as you go.
Design Tip

A good class is a specialist, not a "do-everything" class. If you find a class collecting unrelated fields (student marks AND printer settings?), split it. One class = one clear responsibility.

Session 04 Summary

  • Class = blueprint (no data memory); object = instance created with new (own field copies).
  • Fields are class-level variables that store each object's state; they persist between method calls.
  • Methods act on the fields of the object they are called on: car.accelerate() changes only car.
  • Professional habit: one class per .java file (Explorer → New File → ClassName.java).
  • Noun/verb analysis converts a problem description into classes, fields and methods.
